<objective>
Close UAT gap G-01-9 (UAT test 2, major). The diagnosis found two causes (`.planning/debug/cmd-near-miss-node-env-missing-mongodb-uri.md`):

1. **Observed, environmental.** `backend/.env` does not exist on the dev machine. It is gitignored, Phase 1 never creates it, and the human-test steps never listed it. So every start command stopped at `requireVar(MONGODB_URI)`. The fix is documentation: list `backend/.env` as a prerequisite and make the env source explicit. Creating it automatically is DEV-01 step 6 in Phase 4 and stays there. This plan never creates, reads, prints or commits `backend/.env`.
2. **Latent, code.** `start:test` was `npm run build && node --env-file=.env.test dist/server.js`. Node never lets `--env-file` override a variable that is already in the environment. After `set NODE_ENV=test && npm run start` in a cmd window, `NODE_ENV="test "` stays set, so `npm run start:test` in that same window boots with testMode false. The near-miss warning then tells the user to run `npm run start:test`, which is the command they just ran. No test caught it, because `buildChildEnv` strips NODE_ENV.

Mechanism chosen (the smallest one that removes cause 2): `start:test` becomes `npm run build && dotenv run -q --override -f .env.test -- node dist/server.js`. The `dotenv` CLI ships with the dotenv@18.0.9 dependency the project already has (`backend/node_modules/.bin/dotenv`), so no package is added. `--override` makes `.env.test` win over the shell for the one key it holds (NODE_ENV). The server's own `import "dotenv/config"` still loads `backend/.env` without override, so the shell still wins for every other variable. `-q` keeps the wrapper silent, so boot failures stay at one stderr line. Probed during planning on Node 24.22.1 and Windows. With NODE_ENV "test " inherited, cmd.exe gives the child "test". A CRLF env file still gives "test". The child's exit code 1 propagates. A missing file exits 1. Without `-q` the wrapper prints an "◇ injected env" stderr line. The single test-mode decision in `env.ts` (D-14) is untouched, and no `process.env` read is added outside `env.ts`.

Why not the alternatives: a cross-platform inline `NODE_ENV=test` does not exist in npm scripts (cmd vs sh) without a new dependency. A custom launcher script would read `process.env` outside `env.ts`. Teaching `env.ts` to detect the env-file flag through `process.execArgv` would put fragile argv parsing next to the D-14 decision. Advice-only would leave start:test unable to do its job.

Deviation to surface to the user (not edited here): `.claude/CLAUDE.md` ("What NOT to use" table and the backend package.json notes) still describes start:test as `node --env-file=.env.test`. That file is user-owned project instructions, so this plan leaves it alone and the SUMMARY must flag the stale note.

Output: the start:test script change, a test-helper launcher that mirrors it (plus a process-tree stop), integration and boot cases for the inherited-NODE_ENV and failure paths, a drift guard, corrected near-miss advice, a `.env.example` header that documents creating `backend/.env`, the D-20 amendment, and runnable human tests.

Decisions implemented: D-14 (kept: one raw exact comparison, no new decision site), D-20 (amended: `.env.test` keeps its content and committed status, and is now loaded with override), D-18/D-19 (start:test boot failures keep one `[LỖI]` line and exit 1), D-17 (health testMode is the observable that the new tests assert).
</objective>

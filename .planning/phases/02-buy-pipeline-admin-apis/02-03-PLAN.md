<objective>
Make V1 and V2 give stock back when the MongoDB order insert fails after stock was taken, without ever handing out stock that was really sold, and leave an audit row for every refund.

Purpose: Without compensation, every E11000 or failed insert leaks one unit (V1 `remainingQty`, V2 Redis stock) and Phase 3's E3 (one user, 10 concurrent requests) would show a leak. The refund rules must prefer undersell to oversell when the outcome is ambiguous.
Output: compensation logic inside the existing V1/V2 `createOrder` catch branches of `purchase.service.ts`, an optional `findOrder` seam, and `compensation.test.ts`.

Decisions implemented: D-08, D-09 (V0 untouched), D-10, D-11, D-12 (including its 2026-11-08 amendment), D-14, D-35. D-35's "qty -5 never increases stock in any mode" case is already proven over HTTP by plan 02-01 (buy.test); this plan does not duplicate it.
Refund failure follows D-12 as amended on 2026-11-08 (user-approved, CONTEXT.md): in every refund branch (V1 and V2, after E11000 and after a non-E11000 error with no order) the service prints one console.error line with saleId, userId and mode and throws a new Error with the original createOrder error as `cause`: `new Error("Hoàn kho thất bại sau lỗi trùng đơn", { cause })` after E11000, `new Error("Hoàn kho thất bại sau lỗi ghi đơn", { cause })` after any other insert error. errorHandler answers both with 500 INTERNAL_ERROR, matching D-06's "failed compensation -> 500" and never 409 DUPLICATE (D-08). One private helper builds both, so the file has a single refund-failure log call site. The D-10 paths where no refund fails are unchanged: a successful refund still ends by rethrowing the original error, and a failed lookup rethrows it with no refund.
Claude's-discretion choices recorded here:
- `findOrder` is a second optional seam next to D-14's `createOrder` (`createPurchaseService({ redis, saleCache, createOrder?, findOrder? })`, default `Order.findOne({ saleId, userId }).lean()`), because D-10's "lookup itself throws" branch cannot be reached on a healthy database otherwise; D-14's stated purpose is exactly this kind of test without mocks in production code. Existing callers are unaffected.
- Failure injection in tests uses real collection validators (`collMod`) on `flash_sales` or `stock_movements`, so the refund-failure and movement-failure branches run against the real code path. For the V1 E11000 refund failure the validator is `{ remainingQty: { $lt: 5 } }` on a stock-5 sale: MongoDB validates the post-update document, so the decrement (5 -> 4) passes and only the refund (4 -> 5) is rejected. This needs no seam, so the same case also runs over HTTP.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| purchase service -> MongoDB order insert | An insert can fail ambiguously (written but reported failed); the refund decision crosses this boundary |
| purchase service -> Redis refund | INCRBY/SREM restore shared stock state that every buyer competes for |
| failure logs -> server console | Failure lines are visible to whoever reads the server output |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-10 | Tampering | compensation after an ambiguous order write | high | mitigate | D-10 lookup by (saleId, userId) before any non-E11000 refund; no refund when the order exists or the lookup throws; tests for all three branches in V1 and V2 assert exact stock and buyer state |

<objective>
Close UAT gap G-01-4. The user rejected the `{}` override. A request that declares `Content-Type: application/json` but carries zero bytes must get 400 `INVALID_JSON`, like any other malformed body. Today body-parser 2.4.0 (behind `express.json()` in Express 5.3.0) hard-codes an empty payload to `{}` in both its strict and non-strict parsers. `backend/src/app.ts:23` mounts the plain `express.json()` with no guard, so `Content-Length: 0`, an empty chunked body and a gzip-of-empty body all reach routing as `{}`. `errors.test.ts:72` was weakened during 01-02, so the 01-02 truth was never enforced.

Mechanism (the one the diagnosis confirmed; the user's binding requirement is the behaviour, not the mechanism): use body-parser's `verify` hook. It runs on the decoded payload buffer for every declared-JSON request that has body framing, including the chunked and compressed cases, and it is skipped for requests with no JSON Content-Type. Rejecting `buf.length === 0` there removes the root cause. A Content-Length pre-check middleware would miss the chunked and gzip cases, and the `strict` option has no effect on the empty special case.

The original rationale for keeping `{}` ("needed for body-less POSTs") is wrong: SPECS §7 buy always sends `{ "qty": 1 }`, and the autocannon pattern sends that same body. The only optional-body POST is the Phase 2 admin reset, which must omit Content-Type when it sends no body. This plan records that rule for Phases 2-4.

- `errors.test.ts`: exact assertions for every framing, plus routing checks for body-less POSTs without Content-Type.

Decisions implemented: D-15 (`INVALID_JSON`, 400, Vietnamese message, `{ message, code }`), per the user's UAT test 4 decision.
